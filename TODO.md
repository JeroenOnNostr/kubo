- **KUBO-184: TEPP extension resolution — `extend` tier publishes but is never enforced (Extend ≡ Interact today)**
  The write path is fully wired: assigning someone the Extend tier ("Inner Circle") publishes a **kind 8710** (mode-A interaction npub-list) permission event on its own d-tag (`${kid}:extend:npub`) carrying the tag `["extend", "8710:as-is"]` (`makeTrustTierUpsert` in `useKuboTeppPublish.ts`, `useTrustAssignments.ts`, `teppMigration.ts`; emitted by `buildEvents.ts`, parsed back into `extendPairs` by `parsePermission.ts`). But nothing on the read side consumes it: `assembleConstruct` in `src/lib/tepp-adapters/construct.ts` is **direct-entries-only** — the doc comment (lines 18–22) explicitly defers single-hop extension resolution to a future `resolveExtensionsAdapter()` that was never written, and `evaluate.ts` contains zero references to extend pairs. Net effect: an Extend person gets exactly Interact treatment; the people *they* trust inherit nothing into the kid's construct. The on-wire data is spec-correct and already published, so this is purely a read-side gap.
  **On-wire shape (so nobody has to re-derive it):** permission kinds are 8710/8712 (interact/view npub, mode A), 8711/8713 (mode B — **forbidden** as extend targets), 8714/8715 (interact/view relay), 8716/8717 (interact/view event) — see `src/lib/tepp/kinds.ts`. The extend tag is `["extend", "<kind>:<mutation>", ...]`: one tag per permission event (multiple pairs allowed inside it), mutation is `as-is` (inherit at same tier) or `to-view` (downgrade inherited entries to view), targets restricted to `EXTEND_TARGET_KINDS`. Kubo currently only ever emits the single pair `8710:as-is`.
  **Implementation direction:** (1) confirm exact fetch semantics from the TEPP spec §Extension tag (v0.1.1) — which of the extend-target's events get pulled (their guardian-published permission events of the paired kind); upstream's PoC extension resolver lives in tepp-webapp's `construct.ts` (deliberately not vendored — see `src/lib/tepp/SOURCE.md`; repo `nostr://npub10av9rgt…/relay.ngit.dev/tepp`, mirror gitworkshop.dev, vendored at commit `c770e74`). (2) Implement `resolveExtensionsAdapter()` alongside `assembleConstruct`: fetch the extend-targets' lists via the pool, merge as `ConstructEntry` with `source: 'extension'` and record `mutationsApplied` — both already in `types.ts` (lines 103–104, 142) waiting for a producer. (3) The evaluator consumes construct entries by kind, so merged extension entries *should* be admitted without `evaluate.ts` changes — verify with a test (extend-target trusts X at interact → kid's construct admits X; `to-view` downgrade; blacklist still wins over an inherited entry). (4) Decide cycle/depth policy — spec is single-hop, keep it single-hop. Note: relay-tier extend folds into the shared 8714 list with no distinct on-wire representation (KUBO-170), so relay extension is out of scope until upstream gives it a wire format.
