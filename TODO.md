- **KUBO-121: Mirror KUBO-110 nostrconnect listener fix into onboarding LoginForm**
  Symptom user hit on a fresh 0.4.2 install: onboarding → Log in → Remote signer → Open signer app → Amber approves → Android returns to Kubo → screen hangs, never navigates to `/onboard/add-kid`. Root cause: KUBO-110 (`e929eb15`, cherry-pick of Ditto's `0d1fe7bb`) only patched `src/components/auth/LoginDialog.tsx`, but KUBO-084 had earlier copy-pasted that component into `src/components/auth/LoginForm.tsx` for inline use on `/onboard/login` (`ParentLoginPage`). The duplicate kept the pre-fix listener — `login` in deps + a `cancelled` cleanup flag — so on every parent re-render the in-flight nostrconnect subscription was torn down and `cancelled` was flipped, causing `onLoginRef.current()` to be silently skipped when Amber's NIP-46 ack finally arrived. `ParentLoginPage.handleLogin` therefore never ran and `setLoggedIn(true)` never fired, leaving the user stranded on the login screen. Fix mirrors LoginDialog's post-KUBO-110 pattern in LoginForm: stable `loginRef` next to `onLoginRef`, deps narrowed to `[nostrConnectParams]`, no `cancelled` closure / no per-render cleanup, success branch gated on `controller.signal.aborted`, and `handleRetry` now aborts the previous controller before generating new params (without it, retrying would leak a stale subscription that could fire `onLogin` for stale params). Also dropped the unused `isWaitingForConnect` state (LoginDialog has no equivalent — the spinner shows whenever `nostrConnectUri` is empty, which already covers the same UI). `tsc --noEmit` and `eslint src/components/auth/LoginForm.tsx` pass. **Not yet device-verified** per [feedback_verify_ui_in_browser.md](../../.claude/projects/-home-jeroen-VScode-workspace-for-building-nostr-apps/memory/feedback_verify_ui_in_browser.md): rebuild + reinstall the APK (`npm run build && npm run cap:sync && cd android && ./gradlew assembleRelease`), uninstall any prior Kubo, install fresh, walk the original repro, and confirm `/onboard/add-kid` is reached after Amber returns. Regression-check the in-app LoginDialog modal too.

- **KUBO-120: Reusable invite codes for kubo testers group (relay-dependent)**
  Today the "Kubo testers" NIP-29 group on `wss://groups.0xchat.com/` is open + public — any NIP-29 client can join from anywhere with the address. We want kubo-app users only. Investigation 2026-05-07: fiatjaf's `relay29` (canonical NIP-29 relay, almost certainly what 0xchat runs) has zero invite-code support — closed groups silently ignore kind 9021, only kind 9000 admin add-user lets anyone in. The relay that does support reusable invite codes is [verse-pbc/groups_relay](https://github.com/verse-pbc/groups_relay) (Rust): `Invite` struct in [src/group.rs:308-339](https://github.com/verse-pbc/groups_relay/blob/main/src/group.rs#L308-L339) carries a `reusable: bool`, and a kind 9009 event with a `["reusable"]` tag creates a multi-use invite ([src/group.rs:1175-1178](https://github.com/verse-pbc/groups_relay/blob/main/src/group.rs#L1175-L1178)). The `["reusable"]` tag is a verse-pbc extension, not in the NIP. Implementation requires either (a) verifying that `groups.0xchat.com` happens to run a relay that honors `["reusable"]` (30-second test: publish 9009 with the tag from the admin key, try to join with two different keypairs using the same code), or (b) standing up a verse-pbc/groups_relay instance under our own domain (e.g. on `relay.kubo.watch`) and migrating the testers group there. Once gated: flip the group to `closed`, bake one reusable invite code into the kubo client as a Vite env var, pass it via `useGroupActions().join(addr, code)` (the `code` parameter is already wired through `sendToGroupRelay` in [src/hooks/useGroupActions.ts:130-155](src/hooks/useGroupActions.ts#L130-L155) and through to the kind 9021 `["code", ...]` tag). The shared-static-code model is bypassable by anyone who extracts it from the bundle, but raises the bar from "trivial" to "trivial-with-one-extra-step" and is proportionate for a tester chat. Don't start this until either (a) we've verified 0xchat's relay or (b) we're ready to operate `relay.kubo.watch` as a NIP-29 relay.
